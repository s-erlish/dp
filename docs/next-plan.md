## A. Remnawave XRAY_JSON — запрос JSON-формата по User-Agent (сквозной фикс)

**Ценность.** Это **скрытый P0-баг end-to-end** (детально — `docs/remnawave-templates-spec.md §0`):
вся машинерия «шаблон → скрытый CUSTOM-профиль → применение routing/DNS» уже собрана и работает,
**но клиент никогда не получает JSON-тело**. Remnawave выбирает формат ответа по `User-Agent`, а форк
шлёт `departament/<version>` (`util/HttpUtil.kt:154-162`, и второй путь `:225-229`), который панель не
сопоставляет с xray-json → возвращается обычный base64-список `vless://`. В итоге операторские
routing/DNS/fragment/balancer **не применяются** — прямой источник жалобы «не работает». Без этого фикса
скрытые шаблоны (`docs/hidden-templates-design.md`) и Russia-mode-надёжность частично бесполезны.

**Точка интеграции.**
- `util/HttpUtil.kt:154-162` и `:225-229` — построение заголовка `User-Agent`.
- `auth/BackendConfig.subscriptionUserAgent` уже есть (`BuildConfig.SUB_USER_AGENT`) — но применяется
  только на auth-пути, не на ручной подписке.
- `dto/entities/SubscriptionItem.userAgent` — per-sub переопределение UA уже существует.

**Что делать.**
1. Для подписок, которые должны отдавать xray-json, слать UA, который панель распознаёт как
   JSON-клиент (согласовать точную строку с оператором Remnawave; часто это Happ-совместимый UA либо
   явный `xray`-маркер). Значение — из `BackendConfig.subscriptionUserAgent` / `SubscriptionItem.userAgent`,
   с осмысленным дефолтом, а не хардкод `departament/<ver>`.
2. Смягчить хрупкую детекцию JSON в `AngConfigManager.parseCustomConfigServer` (сейчас требует
   одновременно `inbounds`+`outbounds`+`routing` как подстроки — `remnawave-templates-spec §1`): принимать
   валидный JSON-объект с `outbounds`, не требуя всех трёх подстрок.
3. (страховка) Чистка остаточного вендорного объекта `remnawave` из тела перед передачей в ядро.

**Сложность:** S. **Риск:** средний — неверный UA может сломать подписки, которым нужен именно base64;
поэтому UA задаётся **per-subscription** (не глобально), с безопасным дефолтом. Не менять формат
хранения шаблонов.

**Приёмочные критерии.**
- Подписка Remnawave с host-bound XRAY_JSON, добавленная в приложение, приходит как JSON, сохраняется как
  locked CUSTOM-профиль, и на подключении в собранном конфиге присутствуют операторские routing/DNS
  (проверка дампом конфига/логом).
- Обычные base64-подписки продолжают работать без регрессий (UA per-sub, дефолт не ломает их).
- Детекция JSON срабатывает на одиночном объекте Remnawave без всех трёх подстрок-маркеров.

## B. Завершение Telegram-auth (укрепление scaffold перед включением бэкенда)

**Ценность.** Scaffold корректен, но `review-05`/аудит (`master-requirements-audit §10`) фиксируют
конкретные дыры, которые обязательно закрыть **до** боевого бэкенда: токены в открытом MMKV, инертные
`refreshIfNeeded()`/401, двойная первичная синхронизация.

**Точки интеграции.**
- `auth/AuthTokenStore.kt:18-29` — сейчас `MMKV.mmkvWithID("departament_auth")` **без cryptKey**
  (есть явный `TODO(security)` в шапке файла).
- `auth/DepartamentApiClientImpl.kt` — маппинг статусов; нет 401-перехватчика.
- `auth/AuthManager.refreshIfNeeded():108-122` — реализован, но нигде не вызывается по 401.
- `auth/SubscriptionSyncManager.kt` + `finishReady()` (`AuthManager.kt:140-146`) — импорт подписки на
  логине; проверить отсутствие двойного `updateConfigViaSub` + `syncOne`.

**Что делать.**
1. **Шифрование токенов at-rest:** ключ из Android Keystore → `MMKV.mmkvWithID(ID, mode, cryptKey)`.
   Токен/refresh/subscription-URL — секреты, не логировать.
2. **401→logout:** OkHttp-`Interceptor` (или проверка в `DepartamentApiClientImpl`), который на 401
   вызывает `refreshIfNeeded()`, а при неудаче — `AuthManager.logout()`; локальное состояние честное.
3. **Дедуп первичной синхронизации:** в `SubscriptionSyncManager.importOrUpdate` не дёргать
   `AngConfigManager.updateConfigViaSub` И `SubscriptionUpdater.syncOne` одновременно на первый импорт.

**Сложность:** S–M. **Риск:** Keystore добавляет compile/runtime-риск (в scaffold намеренно опущен) —
обернуть в try/catch с graceful-фолбэком; не блокировать вход, если Keystore недоступен.

**Приёмочные критерии.**
- Токен на диске зашифрован (MMKV cryptKey); dump файла не содержит plaintext-токена.
- Ответ 401 от бэкенда → одна попытка refresh → при неудаче автоматический logout и очистка managed-sub.
- Первичный импорт подписки после логина не порождает двойной сетевой фетч.
- Приложение полностью работоспособно при пустом `BACKEND_BASE_URL` (регрессий нет).

## C. Экран «Аккаунт» + logout + баннер истечения подписки

**Ценность.** Сейчас на Хоуме есть чип аккаунта (`ui/MainActivity.kt:457-468`), но нет полноценного экрана
профиля и **нет выхода из аккаунта** и **нет предупреждения об истечении** прямо на экране коннекта. Это
основа для платежей (D): пользователь должен видеть статус/срок и иметь кнопку «Продлить».

**Точки интеграции.**
- `ui/MainActivity.kt:472-482` — `subscriptionStatusLine()` уже вычисляет активна/до/истекла.
- `auth/AuthTokenStore.getUser()`, `managedSubGuid()`, `getExpiresAt()`.
- В `telegram-auth-design §3.6` логаут спроектирован в `SettingsActivity` — но кастомная Incy-настройка
  уже заменяет legacy (`master-requirements-audit §3`), поэтому логаут вешать в новый settings-tab.

**Что делать.**
1. Экран/боттомшит «Аккаунт»: имя/username из Telegram, статус подписки, срок, использованный трафик,
   кнопки «Продлить» (→ D), «Обновить» (re-pull), «Выйти» (`AuthManager.logout()`).
2. Баннер «Подписка истекает через N дней» / «истекла» на Хоуме (переиспользовать `announce`-механику
   мета-бара, которая уже отрисована) — за порогом ≤3 дней.
3. Пустой/гость-стейт: если `!isLoggedIn()` и бэкенд сконфигурирован — CTA «Войти через Telegram».

**Сложность:** M. **Риск:** низкий; не показывать баннер, когда бэкенд не сконфигурирован и подписка
добавлена вручную без даты.

**Приёмочные критерии.**
- Из аккаунт-чипа открывается экран профиля с реальными данными; «Выйти» очищает сессию и managed-sub.
- При сроке ≤3 дней на Хоуме виден корректный баннер; после продления баннер исчезает после re-pull.
- Всё на русском; при неконфигурированном бэкенде экран/баннер не навязываются.

## D. Внутренние ПЛАТЕЖИ — покупка/продление подписки в приложении

**Ценность.** Прямой запрос заказчика. Даёт монетизацию без ухода в браузер. `telegram-auth-design §5`
уже даёт scaffold-интерфейсы (`PaymentGateway`/`PaymentManager`, endpoints `plans`/`invoice`) — этот
пункт превращает их в рабочую поверхность.

### Клиентская поверхность (что строим в приложении)
- **`PaymentGateway` интерфейс** (уже намечен) с реализациями:
  - `TelegramInvoiceGateway` — **рекомендованный основной путь**: приложение открывает invoice-deep-link
    бота (`https://t.me/<bot>?start=pay_<planId>` или прямой invoice-URL), пользователь платит внутри
    Telegram (Stars/Telegram Payments/провайдер), бот продлевает подписку → приложение делает
    **re-pull** `getSubscription()`. **Минимум клиентского кода, нет PCI, нет риска стор-политики.**
  - `ExternalCheckoutGateway` — Custom Tab на hosted-checkout (YooKassa/Cryptomus/Stripe link) с
    возвратом и re-pull. Провайдер — на стороне бэкенда.
  - (флаг, отдельное решение) Google Play Billing — политика Play по VPN/подпискам + ревшар делают это
    **осознанным отдельным выбором**, не по умолчанию.
- **`PlansActivity`** — карточки тарифов (цена/срок/текущий срок действия), кнопка «Оплатить» →
  открытие pay-flow → возврат → `subs.importOrUpdate(getSubscription())` обновляет серверы и срок.
- **DTO:** `PlanDto`, `PurchaseIntent`, `PurchaseResult`, `InvoiceDto` (§3.1/§5) + два метода в
  `DepartamentApiClient`: `listPlans(token)`, `createInvoice(token, req)`.
- Интеграция с C: кнопка «Продлить» на экране «Аккаунт» и на баннере истечения ведут в `PlansActivity`.

### Что должен предоставить бэкенд (контракт)
- `GET /billing/plans` → `[{id, title, priceLabel, durationDays, currency}]`.
- `POST /billing/invoice {token, planId, deviceId}` → `{invoiceId, payUrl|deepLink, provider}`.
- Продление подписки происходит **на стороне бота/панели** (webhook провайдера → Remnawave продлевает
  срок/лимит). Клиент узнаёт результат **только через `getSubscription()`** — не доверять клиентскому
  «успеху» оплаты (никогда не разблокировать локально без серверного подтверждения).
- (опц.) `GET /billing/status/{invoiceId}` для polling статуса, если deep-link не возвращает управление.

**Сложность:** L (клиент S–M на Telegram-invoice-путь; L — из-за экранов, DTO, состояний оплаты и
серверного контракта). **Приоритет:** P1. **Риски.**
- **Стор-политика (Google Play)**: продажа цифровой подписки в обход Play Billing нарушает политику для
  Play-сборки — держать Telegram/внешний checkout только во flavor вне Play, либо принять риск осознанно.
  Форк уже имеет `productFlavors` (`app/build.gradle.kts:58-67`, fdroid/play) — платёжный gateway
  выбирать по flavor.
- **Не разблокировать доступ по клиентскому «оплачено»** — только по серверному re-pull.
- Идемпотентность invoice (двойной тап не создаёт два платежа).

**Приёмочные критерии.**
- `PlansActivity` показывает тарифы с бэкенда; тап «Оплатить» открывает Telegram-invoice/checkout.
- После оплаты и возврата re-pull `getSubscription()` обновляет срок/трафик/серверы; UI отражает новый срок.
- Ни при каких условиях доступ не расширяется без серверного подтверждения.
- В Play-flavor платный путь либо соответствует Play Billing, либо скрыт; всё на русском.

## E. Автоподключение при запуске + always-on / Kill-switch surface

**Ценность.** `master-requirements-audit §4a` (S5-детали) требует экран «Соединение» с
Автоподключение / Автоподключение при загрузке / **Kill Switch** / LAN / хотспот. Волна 3 это **не
покрывает**. Автозапуск-на-boot уже есть (`BootReceiver`), но **нет автоконнекта при запуске приложения**
и **нет поверхности kill-switch**.

**Точки интеграции.**
- `receiver/BootReceiver.kt` — паттерн гейта `MmkvManager.decodeStartOnBoot()` уже есть; аналогично ввести
  `PREF_AUTO_CONNECT_ON_LAUNCH`.
- `ui/MainActivity.kt` `onCreate` / `handleFabAction` — точка автостарта после выбора сервера.
- `service/CoreVpnService.kt:62-71` (`setUnderlyingNetworks`) — уже управляет сетями; Kill-switch на
  Android честнее всего реализуется через системный **Always-on VPN + «Block connections without VPN»**
  (`VpnService`), а не самопальной блокировкой.
- `AppConfig.kt` — новые prefs.

**Что делать.**
1. **Автоконнект при запуске** (`PREF_AUTO_CONNECT_ON_LAUNCH`): если сервер выбран и разрешение выдано —
   стартовать сервис в `onCreate` (не показывать праймер повторно; уважать одноразовость).
2. **Kill-switch surface**: не изобретать блокировку в приложении, а **вести пользователя в системные
   настройки Always-on VPN** (deep-link `Settings.ACTION_VPN_SETTINGS`) + короткое честное объяснение,
   плюс убедиться, что сервис корректно объявлен как always-on-совместимый. Опционально — «мягкий»
   in-app kill-switch: при обрыве не пускать трафик мимо (требует аккуратной работы с маршрутами; отметить
   как более рискованный под-пункт).
3. Собрать экран «Соединение» (S5) с рядами: Автоподключение / При загрузке (уже есть) / Kill Switch /
   Разрешить LAN / Доступ через хотспот — в ките `bg_card_incy`.

**Сложность:** M. **Риск:** самопальный kill-switch легко даёт «дыры» (трафик в момент реконнекта) —
предпочесть системный Always-on. Автоконнект не должен конфликтовать с онбордингом/праймером (волна 3 §2).

**Приёмочные критерии.**
- С включённым автоконнектом запуск приложения при выбранном сервере автоматически поднимает VPN.
- Ряд Kill-switch открывает системные VPN-настройки; объяснение честное (без «непробиваемости»).
- Экран «Соединение» на русском, согласован с ситайл настроек; существующий boot-autostart не сломан.

## F. Напоминания об истечении подписки (WorkManager-нотификации)

**Ценность.** Прямое требование задачи (Data). Удерживает платящих: заранее предупредить «подписка
истекает» → тап ведёт в `PlansActivity` (D). Инфраструктура периодических задач уже есть.

**Точки интеграции.**
- `handler/SubscriptionUpdater.kt` — уже гоняет `PeriodicWorkRequestBuilder<UpdateTask>`; после каждого
  апдейта известны `SubscriptionItem.expire` (epoch seconds).
- `handler/NotificationManager.kt` — уже строит нотификации (переиспользовать канал/иконки).
- `auth/AuthTokenStore.getExpiresAt()` — срок из auth-сессии как второй источник.

**Что делать.**
1. Отдельный лёгкий периодический воркер (или хук в существующий `UpdateTask.doWork`), проверяющий
   ближайший `expire`; при пересечении порогов (например, 3 дня / 1 день / истекла) — локальная
   нотификация «Подписка истекает N дней» с тапом в аккаунт/тарифы.
2. Дедуп: не слать одну и ту же нотификацию повторно (флаг «последний уведомлённый порог» в MMKV).
3. Гейт флагом `PREF_SUB_EXPIRY_REMINDERS` (по умолчанию on); уважать POST_NOTIFICATIONS (Android 13+).

**Сложность:** S–M. **Риск:** спам-нотификации без дедупа; часовой пояс/пороги. Не слать, если срок не
известен (безлимит/ручная подписка без даты).

**Приёмочные критерии.**
- За 3 дня до истечения приходит одна нотификация; повтор того же порога не дублируется.
- Тап открывает экран аккаунта/тарифов; после продления (новый `expire`) пороги сбрасываются.
- Флаг отключает напоминания; на Android 13+ уважается разрешение на нотификации.

## G. Быстрый коннект к лучшему серверу + перф на слабых устройствах

**Ценность.** Требование задачи (Performance): быстро подключаться к лучшему серверу и не жрать память на
low-end. Fast-connect уже есть (`viewmodel/MainViewModel.fastConnect`), но выбор «лучшего» и дисциплина
памяти можно усилить.

**Точки интеграции.**
- `handler/SpeedtestManager.kt` — методы пинга (TCP/ICMP/HTTP/real); `review-03`/`review-04` фиксируют:
  per-server OkHttp client (churn), HTTP-метод бьёт по одному фикс-URL и не различает серверы.
- `ui/MainActivity.kt:974` `scheduleHealthCheckIfEnabled`, `:238-271` авто-фолбэк.
- `util/MemoryStatsManager.kt`, 2s-поллинг (`master-requirements-audit §13b`).

**Что делать.**
1. **Параллельный ранжирующий скан** перед fast-connect: замерять кандидатов конкурентно (ограниченный
   пул), выбирать по реальной достижимости (>16 КБ, `ping_method_real`), а не по TCP-пингу (перекликается
   с волной 3 §6d liveness). Кэшировать последний лучший, чтобы «умный коннект» был мгновенным.
2. **Один общий `OkHttpClient`** для пинга/подписок вместо билда на каждый сервер (`review-03 MEDIUM`) —
   прямой выигрыш по памяти/GC на слабых.
3. **Ленивая загрузка иконок/флагов** и отказ от удержания полных списков Drawable (перекликается с
   волной 3 §3 split-tunnel и §13b).
4. Профиль холодного старта: отложить некритичную инициализацию (виджет/чек апдейтов) с главного пути.

**Сложность:** M. **Риск:** параллельный скан = всплеск трафика/батареи — ограничить пул и гейтить.
Не ломать существующий однократный health-check/канал `MSG_MEASURE_DELAY` (общий канал — известный
MEDIUM из `review-04`; ранжирование должно использовать отдельный тег результата).

**Приёмочные критерии.**
- «Умный коннект» выбирает реально живой (>16 КБ) сервер, а не первый по TCP; повторный вызов мгновенен
  из кэша.
- Один OkHttpClient переиспользуется; при 15+ серверах нет заметного роста ОЗУ во время скана.
- Холодный старт не деградирует; прокрутка списков плавная на low-end.

## H. Полировка quick-tile и виджета

**Ценность.** Быстрый коннект с домашнего экрана/шторки — заметная parity-мелочь. Компоненты **уже
существуют** (`service/QSTileService.kt`, `receiver/WidgetProvider.kt`), но их состояние/полировку стоит
довести до Incy-качества.

**Точки интеграции.**
- `service/QSTileService.kt` — состояние тайла (active/inactive/unavailable), лейбл.
- `receiver/WidgetProvider.kt` + `res/xml/app_widget_provider.xml` — обновление по broadcast состояния.
- `handler/NotificationManager.kt` шлёт `MSG_STATE_*` — источник для синхронизации тайла/виджета.

**Что делать.**
1. Тайл: три честных состояния (отключено/подключается/подключено), правильный лейбл сервера, тап =
   toggle; синхронизация с реальным состоянием сервиса.
2. Виджет: показывать выбранный сервер + флаг, состояние коннекта, опц. live ↑/↓; тап по виджету =
   коннект/дисконнект (как щит на Хоуме).
3. Единый источник состояния (переиспользовать broadcast из сервиса), без отдельного поллинга.

**Сложность:** S–M. **Риск:** рассинхрон состояния тайл/виджет/нотификация — завязать всё на один
broadcast. Виджет на разных лончерах — проверить тёмную/светлую тему.

**Приёмочные критерии.**
- Тайл и виджет отражают реальное состояние в реальном времени; тап подключает/отключает.
- Смена сервера/темы корректно перерисовывает виджет; нет «залипших» состояний.

## I. Расширенная надёжность под РКН поверх волны 3

**Ценность.** Волна 3 §6 закрывает Russia-mode (fragment/uTLS/mux) + периодический liveness. Здесь —
**дельта, которую волна 3 не трогает**, но которая реально помогает под TSPU (июль 2026).

**Точки интеграции.**
- `core/CoreOutboundBuilder.kt` — TLS/fragment (уже точки из волны 3 §6).
- Парсер директив подписки (`util/HttpUtil.kt`, `AngConfigManager`) — Incy `sort-order` (§incy-analysis 1.1).
- DNS-настройки конфига (`core/CoreConfigManager`/DNS-секция).

**Что делать (только реалистичное, что ядро умеет).**
1. **DNS-leak дисциплина**: гарантировать, что резолвинг идёт через тоннель (DoH/удалённый DNS в
   конфиге), а не через системный резолвер оператора — типичная утечка, палящая факт VPN.
2. **`sort-order: ping|name|none`** из заголовка подписки (Incy-экстра, `incy-analysis §1.1`) — уважать
   при сортировке серверов; «ping» переиспользует ранжирование из G.
3. **Per-node liveness memory**: помечать ноды, которые проходят TCP, но «замерзают» (>16 КБ фейлит), и
   понижать их в авто-выборе на время (перекликается с волной 3 §6d, но добавляет **память о плохих
   нодах**, а не только разовый свитч).
4. (долг, не делать сейчас) AmneziaWG/новые UDP-протоколы — нет в форке; отметить.

**Сложность:** M. **Риск:** переопределение DNS может сломать split-DNS/локальные ресурсы — уважать LAN.
Память о «плохих нодах» должна истекать (нода могла восстановиться).

**Приёмочные критерии.**
- При активном VPN DNS-запросы не утекают в системный/операторский резолвер (проверка dns-leak-тестом).
- `sort-order` из подписки применяется к порядку серверов.
- «Замороженная» нода понижается в авто-выборе и восстанавливается по TTL.

## K. Кросс-платформенная подготовка (Windows/Linux/iOS)

**Ценность.** Заказчик хочет будущий выход на десктоп/iOS (`master-requirements-audit §13c`). Сейчас
логика связки «auth → подписка → конфиг → ядро» уже относительно изолирована — правильные швы сегодня
удешевят порт завтра. Это **структурная подготовка, не порт**.

**Точки интеграции (что уже удачно изолировано).**

  слой, который переиспользуется на любой платформе** — не тащит Android-UI.
- `core/CoreOutboundBuilder`, `CoreConfigManager` — построение xray-конфига (переносимая логика поверх
  того же Xray-core).

**Что делать (без переписывания).**
1. **Не размывать контракт бэкенда**: держать все URL/endpoints в `BackendConfig` (уже так), не
   разбрасывать по активити (`telegram-auth-design §4`). Это единственный файл, который меняется при
   смене окружения — сохранить это свойство.
2. **Держать auth/subscription-логику Android-free**: `AuthManager`/`SubscriptionSyncManager` не должны
   зависеть от `Activity`/`View` — сейчас в основном так; зафиксировать как правило (только `MMKV` как
   Android-зависимость → при порте заменяется на аналог хранилища).
3. Документировать «портируемое ядро»: контракт API + формат конфига + модель подписки — как отдельный
   слой, который на десктопе оборачивается своим UI (Xray-core уже кроссплатформенный).
4. iOS — отдельный клиент поверх того же бэкенд-контракта и того же формата подписки Remnawave
   (не общий Kotlin-код без KMP; KMP — осознанное отдельное решение).

**Сложность:** M (в основном дисциплина + документ). **Приоритет:** P3. **Риск:** преждевременная
абстракция ради кросс-платформы удорожает Android сейчас — **не рефакторить агрессивно**, только держать
границы чистыми и задокументировать контракт.

**Приёмочные критерии.**
- Все сетевые URL/endpoints централизованы в `BackendConfig` (ни одной захардкоженной вне него).
- `AuthManager`/`SubscriptionSyncManager` компилируются без ссылок на `android.view`/`Activity`.
- Есть краткий документ «портируемый core-контракт» (API + формат подписки + конфиг).
