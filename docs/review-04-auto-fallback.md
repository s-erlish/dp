# Review 04 — Module 3 auto-fallback + ping polish

Commits: `52a67a1` (auto-fallback to a working server) and `197a4d1` (per-node direct HTTP ping polish).
Scope: `V2rayNG/`. Read-only review (no Android SDK; findings by code reading).

## Verdict

- **Compile:** clean. No compile errors found in either commit.
- **Reconnect loop: POSSIBLE — this is a BLOCKER.** The "once per session" guard (`autoFallbackDone`) is reset by the fallback's own restart, so a server whose tunnel stalls but whose independent config-test passes (exactly the RKN "connect then stall" case the feature targets) causes an unbounded switch/restart loop.

## Findings

| Severity | File:line | Issue | Fix |
|---|---|---|---|
| **BLOCKER** | `ui/MainActivity.kt:194`, `:200-203`, `:374-378` | **Reconnect loop.** `resetAutoFallback()` (which sets `autoFallbackDone = false`) runs on *every* `isRunning == false`. The fallback itself calls `triggerFastConnect()` → `fastConnectAction` → `restartV2Ray()` → `stopVService()`, which broadcasts `STOP_SUCCESS`/`NOT_RUNNING` → `isRunning = false` → `resetAutoFallback()` clears `autoFallbackDone`. On the subsequent `START_SUCCESS` a new 7s health check is armed with `autoFallbackDone == false`, so if the newly selected server also fails the tunnel health check it falls back again → infinite loop. `fastConnect` picks the fastest server by `testAllRealPing`, which measures each config through a **separate temporary core** (independent of the live tunnel). In the RKN pattern the handshake/config-test succeeds (positive latency) while the live tunnel stalls, so `selectFastestServer()` keeps returning a guid (possibly the *same* stalling server) → the loop never terminates. Commit message's "once per session (no reconnect loops)" is not achieved. | Distinguish the fallback-initiated restart from a user stop: e.g. keep `autoFallbackDone` set across the restart (only clear it on a user-initiated disconnect, not on the internal stop/start), or gate on a dedicated `fallbackInProgress` flag so `resetAutoFallback()` does not fire during the restart. Also ensure fallback never re-selects the server that just failed. |
| **HIGH** | `ui/MainActivity.kt:57-58`, `:194`, `onSaveInstanceState` (absent for these fields) | **State lost on recreate defeats once-per-session and re-arms fallback.** `autoFallbackDone`/`healthCheckPending` are plain Activity fields, not persisted in `onSaveInstanceState` (only `KEY_CONNECTION_START` is). On rotation/theme change the new Activity re-observes `isRunning`, LiveData replays `true`, and `scheduleHealthCheckIfEnabled()` runs with `autoFallbackDone == false` — re-arming a fresh health check and a possible second fallback mid-session even after one already occurred. | Persist `autoFallbackDone` (and ideally connection-session identity) across recreate, or hold this state in the ViewModel rather than the Activity. |
| **MEDIUM** | `ui/MainActivity.kt:59-64`, `:196-204`; `core/CoreServiceManager.kt:~360` | **Single transient failure needlessly switches a working connection.** The 7s check triggers fallback whenever `measureDelay` returns `time < 0`. `measureDelay` retries only the two delay-test URLs; a transient failure of the delay-test endpoint (blocked/slow test URL, momentary DNS) at the 7s mark forces a full restart + server switch even when the tunnel is otherwise healthy. | Require N consecutive failures, or re-probe once before switching; consider a longer/again-check window. |
| **MEDIUM** | `viewmodel/MainViewModel.kt:258-260`, `612-616`; `ui/MainActivity.kt:197-204`, `handleLayoutTestClick` | **`MSG_MEASURE_DELAY` result channel is shared with the manual "test connection" tap.** Both the health check and a user tap send `MSG_MEASURE_DELAY` and both consume `MSG_STATE_DELAY_RESULT`/`healthCheckPending`. A manual tap while a health check is in flight (or vice-versa) can cross-consume results: a user tap returning `-1` could trigger a false fallback, or consume the pending flag so the real health-check result is dropped. | Tag the health-check request (distinct `what` or a correlation token) so the observer only reacts to its own probe. |
| **MEDIUM** | `viewmodel/MainViewModel.kt:283-286` (commit `197a4d1`) | **`https://host:port/` probe misclassifies non-TLS-HTTP nodes.** Many VMess/VLESS/Trojan nodes do not speak HTTPS on their transport port; a TLS handshake to `serverPort` fails → `-1` even though the node is reachable via its actual protocol. Direct HTTP reachability therefore still under-reports for such nodes (partial fix of review-03). | Acceptable as a heuristic, but document the limitation; consider falling back to TCP connect when the HTTP probe fails, or only using this method where TLS/HTTP is expected. |
| **LOW** | `viewmodel/MainViewModel.kt:612-615` | `getSerializableExtra(String) as? Long` is deprecated on API 33+ (typed overload preferred). Compiles with a warning; consistent with the existing `LongArray` handler. | Use the `getSerializableExtra(name, Long::class.java)` overload guarded by SDK version if warnings are to be cleared. |

## Loop trace (BLOCKER, explicit)

connect → `START_SUCCESS` → `isRunning=true` → `scheduleHealthCheckIfEnabled()` (autoFallbackDone=false) → +7s `healthCheckRunnable` sets `healthCheckPending=true`, `testCurrentServerRealPing()` → core `measureDelay` returns `-1` (tunnel stalls) → `MSG_STATE_DELAY_RESULT(-1)` → observer: enabled && !autoFallbackDone && time<0 → `autoFallbackDone=true`, `triggerFastConnect()` → `testAllRealPing` (separate cores) returns a positive latency for some/the-same server → `fastConnectAction(guid)` → `restartV2Ray()` → `stopVService()` → **`isRunning=false` → `resetAutoFallback()` clears `autoFallbackDone`** → +500ms `startV2Ray()` → `START_SUCCESS` → `isRunning=true` → `scheduleHealthCheckIfEnabled()` **(autoFallbackDone=false again)** → +7s health check fails again → fallback again → **loop**.

Loop terminates only if `testAllRealPing` returns no valid latency for any server (`fastestGuid == null` → observer shows failure toast, no restart). Whenever at least one config-test passes while the live tunnel stalls — the exact RKN scenario — the loop is unbounded.
